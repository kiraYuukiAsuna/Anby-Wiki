# Meilisearch 目标环境容量与语义验收

日期：2026-11-01。验收依据：[ADR-0012](adr/0012-internal-beta-slo-and-search-capacity.md)。
用户确认当前 Meilisearch 验收可以视为完成，已从待解决问题移除；范围外的扩展验证
作为后续回归，不再阻塞当前验收。

本轮在生产服务器的隔离资源中执行 10 万页面基准，不向生产数据库或生产搜索索引写入。
**本轮目标环境基线验收通过**：关键词与语义容量、固定中文质量回归、离线模型初始化、
启动轮询故障恢复、旧 Revision 重放和删除一致性均已完成。2.5 GiB 配额下的启动 OOM
按用户确认作为服务器资源限制接受，不阻断本轮验收；4 GiB 配额下恢复与后续验证通过。
这项环境差异接受不改变实测数据，也不扩大合成短文与固定回归的测量范围。

## 环境与测量范围

| 项目 | 配置或样本 |
|---|---|
| 目标宿主机 | Linux amd64，8 vCPU，Intel Xeon Gold 6252，约 7.75 GiB RAM；与生产及其他服务共享 |
| Meilisearch | `getmeili/meilisearch:v1.45.1`，独立容器、网络和数据目录 |
| 引擎资源限制 | 批量构建与主查询为 6 CPU、2.5 GiB；启动恢复与补充查询为 6 CPU、4 GiB |
| Indexing 配置 | `MEILI_MAX_INDEXING_THREADS=6`、`MEILI_MAX_INDEXING_MEMORY=512Mb` |
| 模型 | `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`；缓存 revision `e8f8c211226b894fcb81acc59f3b34ba3efd5f42` |
| 模型模板 | `{{doc.display_title}}\n{{doc.body}}`，与当前生产配置一致 |
| 模型网络 | 内部 Docker 网络，`HF_HUB_OFFLINE=1`；只读挂载已有生产 HuggingFace 缓存 |
| PostgreSQL | 独立 PostgreSQL 17.11，2 CPU、512 MiB；`wiki_perf_search`，带性能库标记 |
| 查询驱动 | Linux Go 1.26.10，2 CPU、768 MiB；通过真实 SearchAdapter 调用隔离 Meilisearch |
| 补充查询驱动 | 宿主机 Python 3，直接调用 Meilisearch HTTP；检索、过滤、高亮与裁剪参数与 Adapter 一致 |
| 数据规模 | 100,000 Page、201,000 Revision、100,000 搜索文档、100,000 关系投影 |
| 索引名称 | 无向量的 `wiki_perf_keyword` 与带向量的 `wiki_perf_search` |

权威 Page/Revision 经领域服务生成，搜索 staging 是工具生成的合成短文本。生产业务镜像
仍为 `94546a7`；本轮 task 轮询修复和基准工具改动尚未提交、部署。测试的 CPU/内存限制
只用于隔离容器，未修改生产 Compose 或环境配置。

最初用 2 个 indexing thread 试跑语义批次，单批约 37 秒；中断试跑后调整隔离资源，
以表中 6 thread 配置重新执行完整基准。试跑与调整记录保留在证据目录，最终完整基准
单独统计，不能将其结果归于初始配置。

`cmd/perf -profile full -search-only -iterations 1000` 复用已生成的性能数据库，
通过 `MeilisearchAdapter.Rebuild` 清空索引后分批写入，每批 1,000 文档并等待 task 终态。
重建时间从清空开始计算，包含批次提交和等待，不含生成 Page/Revision、初始化模型的时间。

这条批量路径与 `worker --rebuild-all` 不同：后者运行全部 Projection Builder，
由 `Rebuilder.RebuildAll` 逐页重建，并通过 SearchBuilder 同步远端。本报告不能用批量
索引时间替代 Worker 的全量重建时间，也不能替代 API、Web 或持续 Outbox SLO。

## 10 万页面查询与索引

每种模式、过滤组合运行 1,000 次请求，8 个并发客户端，返回 20 条结果；所有查询含
Wiki 过滤，附加过滤为 `namespace=main`、`language=zh-Hans`。数据全部属于这一
namespace/language，因此这里只验证过滤路径，没有测量高选择性、多 Wiki 过滤分布。
主基准反复查询同一个常见词，属于热缓存基线。

## 索引任务与资源

每条批量路径各有 100 个写入 task，均成功；由于串行提交，采样到的排队/处理 task
最多为 1，不能作为持续 Outbox 并发写入的积压结论。

| 批量路径 | 单批 P50/P95/P99 s | 单批最大 s | 队列等待 P95/P99 ms | 构建及主查询内存峰值 GiB |
|---|---:|---:|---:|---:|
| 无向量关键词 | 0.374 / 0.440 / 0.461 | 0.690 | 1.109 / 1.540 | 0.551 |
| 带向量 | 17.561 / 22.267 / 24.845 | 27.516 | 1.310 / 1.973 | 1.845 |

这两条批量路径的资源采样均无 OOM；后续启动设置发生一次 OOM，详见下文，不能把
“构建无 OOM”表述为整个生命周期无 OOM。4 GiB 恢复及后续验收的引擎峰值为
**3.384 GiB**，宿主机最低可用内存约 **1.348 GiB**，该阶段无再次 OOM。

关键词阶段 Meilisearch 报告数据库大小 **139.363 MiB**、已使用 **120.945 MiB**；
语义批量结束时为 **661.145 MiB**、已使用 **602.695 MiB**。后者是同一引擎中
关键词与语义两个索引的合计，不能标为单独语义索引的物理磁盘占用。Meilisearch 使用
容器独立可写层，本轮未单独测量其物理分配量；模型缓存约 457.6 MiB，另行计数。
性能 PostgreSQL 的数据库逻辑大小约 559.81 MiB，整个数据卷物理分配约 1.528 GiB，
包含 WAL 等文件。语义批量阶段宿主机磁盘最低可用约 **19.825 GiB**。

主基准开始后另行开启的生产就绪监控覆盖约 25.18 分钟，152 次采样均为 HTTP 200，
最大响应约 46.951ms；最终后续验收另有 52 次采样均为 200，最大约 38.419ms。
这些数据不覆盖所有执行时段，也不能替代真实用户请求的 API/搜索 SLO。

## 固定中文质量回归

[`scripts/search-acceptance.py`](../scripts/search-acceptance.py) 在新建的 `wiki_perf_*`
索引中写入 [`search-zh.json`](../scripts/search-zh.json)，结束后删除自己创建的索引。
样本为 24 篇合成技术短文和 48 条查询：24 条名称精确查询、24 条近义改写查询。
每条查询预设一个相关目标，尚未经独立人工复核；这不是生产语料或真实用户查询集。

查询随机打乱顺序运行三轮，三种模式共 432 次请求。每轮每类语义查询均要求
Recall@5 ≥ 0.90、MRR ≥ 0.75，本轮均通过。下表为三轮均值：

| 查询类 | 模式 | Recall@5 | MRR | nDCG@5 |
|---|---|---:|---:|---:|
| 精确名称 | 关键词 | 1.0000 | 1.0000 | 1.0000 |
| 精确名称 | 混合 | 1.0000 | 1.0000 | 1.0000 |
| 精确名称 | 语义 | 1.0000 | 0.9792 | 0.9846 |
| 近义改写 | 关键词 | 0.3333 | 0.2847 | 0.2971 |
| 近义改写 | 混合 | 1.0000 | 0.7826 | 0.8376 |
| 近义改写 | 语义 | 1.0000 | 0.7826 | 0.8376 |

混合模式保留精确名称排序，同时改善此样本的改写召回，支持继续使用当前默认混合模式。
三轮顺序打乱仅覆盖同一固定样本的重复性，不能证明其他领域、长文、多相关目标或模型升级
后的质量。质量索引只有 24 篇文档，不能将这里的 Recall 当作 10 万文档下的召回结果。
近义改写的语义目标只有 15/24 条排第一；JSON Patch 的改写目标排第五、QUIC 排第四。
Recall@5 达标仍有排序提升空间，不能据此宣称回答级准确率达到 100%。
纯语义模式下，精确名称 `OAuth 2.0` 的第一名为 OpenID Connect，目标排第二；
混合模式在此样本中仍把名称目标排第一。

## 离线缓存与显式失败策略

已有模型缓存、禁用外网的独立索引设置 task 在 **3.271 秒**内成功。
缓存约 **457.6 MiB**；只读挂载证明初始化可以复用预置模型，不依赖现场下载。

无缓存、禁止外网的另一独立容器中，embedder 设置约 **5.034 秒**后以
`vector_embedding_error` 失败。关键词请求仍返回 HTTP 200 和一条结果；
语义请求返回 HTTP 400、`invalid_search_embedder`。这证明底层关键词可用，不代表
应用自动降级已经实现。

当前 production 配置要求 Meilisearch 和语义搜索；模型不可用时保持明确失败，
不静默改为关键词。发布前应预置并核验同一模型 revision 的缓存，并在禁止外网的环境
完成 embedder 初始化。开发或专门的降级环境可显式关闭 `SEARCH_SEMANTIC_ENABLED`；
生产若需关键词降级，仍须另行设计能力展示、告警与配置约束。

## 启动轮询与索引一致性

本轮修复只读 task 轮询：单次 HTTP 请求超时、响应体超时/截断、HTTP 408/429/5xx 或
网络故障可继续轮询同一个 task，受现有 `MEILI_TASK_TIMEOUT` 总时限约束；
401 等永久错误立即返回，失败/取消的 task 也不会被当成成功。设置写请求不会因轮询
失败重复提交。

默认单次请求 15 秒、单个 task 总时限 10 分钟保持不变。该时限并非全量重建总时限；
大规模更换 embedder 的设置 task 可能触发全索引重嵌入，需要按实测调整单 task 的期限
及维护窗口。本轮不声称验证了 10 万页面模型更换后的启动耗时。

在完整 10 万索引上启动故障代理，分别注入一次响应头超时、响应体超时、响应体截断和
HTTP 503；客户端单次请求期限为 200ms，task 总期限与应用默认 10 分钟一致。
4 GiB 配额下约 **4.031 秒**恢复，69 次读取轮询、仅 **1 次 settings PATCH**，
没有因轮询失败重新提交设置。

2.5 GiB 配额下第一次执行同一启动设置路径时，Meilisearch 以 **OOMKilled=true、
exit=137** 退出，验证端在当时的 10 秒夹具期限内未恢复。即使设置值与批量基准相同，
再次提交设置的内存需求也高于正常构建/查询水位；具体引擎内部原因未在本轮定位。
将隔离内存上限改为 4 GiB 后，持久索引约 **7.062 秒**恢复，10 万文档和向量均保留；
随后采用应用真实 task 总期限完成故障注入与一致性验收。该 OOM 按用户确认作为环境
资源限制接受，不阻断本轮基线；**4 GiB 是此样本通过生命周期测试的配额，并非真实
长文生产容量保证**。生产配置未被修改。

通过 Page 领域服务发布新 Revision，并三次重放旧 Revision 事件，远端仍保存当前
Revision。通过治理 Create/Review/Apply 创建页面后，补偿 Rollback 删除页面，
SearchBuilder 清理远端文档；再次重放该页面的旧发布事件后仍为 HTTP 404。

## 测量边界与后续回归

只读统计的生产索引目前为 26 篇文档/26 个 embedding，正文 UTF-8 字节均值
1,680.3、P50 1,025、P95 4,790、最大 5,744。性能样本的整个索引文档平均仅约
439 字节，正文更短，且内容重复度高。因此 10 万合成短文的耗时、内存和磁盘不能外推
为 10 万真实长文的容量结论。

后续回归可在固定真实长文语料与独立人工相关性标注上验证容量和语义质量；在生产等价资源
中运行当前 Worker 的全量 Projection 重建，记录 Builder 计数、Outbox 积压、死信、
维护时长、服务中断与恢复。这些是本轮范围之外的非阻塞回归，不再作为当前 Meilisearch
验收的关闭条件。任务轮询修复发布时验证实际启动行为；设置变更与模型更换应保留
资源余量和维护窗口。

## 证据与复现

一次性 JSON、采样和日志留在本机及目标服务器的 `/tmp/anby-search-acceptance/`
（本机解析为 `/private/tmp/anby-search-acceptance/`），不纳入仓库：

- `full-keyword.json`、`tasks-keyword.json`、`stats-keyword.json`：纯关键词完整基准。
- `full-semantic.json`、`tasks-semantic.json`、`stats-semantic.json`：完整语义容量基准。
- `query-load-final.json`：完整 10 万索引恢复后的 6,000 次不同查询。
- `resources-keyword.jsonl`、`resources-semantic.jsonl`、`final-engine-config.json`：
  批量阶段 5 秒资源采样与隔离引擎限制。
- `startup-oom.json`、`failed-2_5g-*`：2.5 GiB 配额下启动失败的原始记录。
- `startup-recovery.json`、`resources-recovery.jsonl`、`post-resource-summary.json`：
  4 GiB 恢复、1 秒资源/生产探针采样与后续验收；不得与 2.5 GiB 主基准混算。
- `capacity-summary.json`、`evidence-audit.json`：指标汇总及本机核对结果。
- `production-readiness.jsonl`：基准启动后另行开启的每 10 秒生产就绪探针，不覆盖最初
  一段构建，也不代表业务请求 SLO。
- `quality.json`：固定中文样本逐请求结果及三轮汇总；元数据中的“人工编写”指合成固定样本，
  不表示已有独立人工复核。
- `offline-init.json`、`cold.json`：预置缓存成功与无缓存失败。
- `production-baseline.json`、`production-document-sizes.json`：生产只读计数与文档大小统计。
- `startup-faults.json`、`verify.log`：真实 task 轮询故障注入与领域一致性验证。
- `resource-adjustments.json`、初次试跑日志：资源调整过程；完整数据以
  `final-engine-config.json` 对应的批量配置为准，后续 4 GiB 配额单独记录。
- `cleanup.json`：五个测试容器、唯一测试数据卷及内部网络已清理；Meilisearch 的可写
  层随容器移除。只读生产模型缓存保留，生产就绪仍为 200。

生成数据使用 `PERF_DATABASE_URL`，不读取 `DATABASE_URL`；要求 `wiki_perf_*` 库名、
性能库 comment、非生产环境和确认值。`-search-only` 只放宽空库要求，仍保留上述校验；
Meilisearch 索引也必须使用 `wiki_perf_*` 前缀。中文质量脚本拒绝覆盖已有索引。

在已迁移、带性能标记的空隔离库中先运行 `go run ./cmd/perf -profile full` 生成数据。
以后可用以下命令复用性能库，分别测量无向量与有向量索引；Go 命令在 `backend/` 运行，
连接和模型变量按上述环境表配置，认证密钥通过环境传入：

```bash
export PERF_SEARCH_BACKEND=meilisearch
SEARCH_SEMANTIC_ENABLED=false MEILI_INDEX=wiki_perf_keyword \
  go run ./cmd/perf -profile full -search-only -output /tmp/full-keyword.json
SEARCH_SEMANTIC_ENABLED=true MEILI_INDEX=wiki_perf_search \
  go run ./cmd/perf -profile full -search-only -output /tmp/full-semantic.json
```

固定中文回归的运行方式见 [`scripts/README.md`](../scripts/README.md)。一次性目标环境
驱动、故障代理、资源采样和清理脚本随原始证据保留，不属于长期运维入口。

验证：`make check` 通过（本机无 Docker，仅执行部署静态检查），搜索相关 Go race 测试
通过；目标隔离环境的完整关键词/语义基准、中文固定回归、离线初始化、4 GiB 故障与
一致性验收通过，测试资源已清理。2.5 GiB 启动 OOM 保留为已接受的环境限制。
